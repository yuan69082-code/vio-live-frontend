# 08｜权限、安全与隐私治理

## 状态

- 文档状态：Permission、Security、Confirmation、AuditLog 与设备授权准备基础已实现；真实资源执行仍在规划
- 权限基础：已完成规则 CRUD、三态 Checker、单次许可消费和事件联动
- 安全基础：已完成四级风险、三种确认要求、确认防重放和最小审计
- 真实账号、Tool 执行和设备连接：未接入；设备主体授权已复用 Permission 数据结构
- 正式上线前需要安全、隐私和法律审查

## 当前权限五档

| `permission_level` | Checker 结果 | 含义 |
| --- | --- | --- |
| `always_allow` | `allow` | 在完全匹配的主体、资源实例和操作范围内允许 |
| `ask_every_time` | `ask` | 每次执行前要求明确确认 |
| `allow_once` | 首次为 `allow`，随后为 `deny` | 独立 Checker 首次判断后消费；Security 预检在确认满足前不消费 |
| `denied` | `deny` | 不允许执行，但 `canAsk=true` |
| `forbidden_ask` | `deny` | 不允许执行且 `canAsk=false` |

总规划原有“本次会话允许”仍属于后续目标，本阶段明确实现的是 `allow_once`，尚未建立会话 ID、会话结束失效或有效期机制。

## 权限粒度

权限不能只做一个总开关，应按以下维度分别表达：

- 用户与智能体主体
- Tool、设备或外部服务
- 数据类型
- 具体动作
- 允许范围
- 有效时间
- 是否可以主动申请

### 当前基础实现

- 每条规则必须绑定用户、主体、资源类型、资源 ID 和具体操作，不支持通配、继承或主体无关规则。
- 资源类型为 `memory`、`tool`、`mcp`、`skill`、`device`、`api`、`private_domain`。
- 基础操作为 `read`、`write`、`execute`、`control`、`connect`、`export`、`delete`、`manage`。
- 状态为 `active`、`inactive`、`consumed`、`deleted`；只有 `active` 参与判断。
- 没有完全匹配的活动规则时默认返回 `deny`，不会因已登录、模型选择或其他资源权限自动放行。

## 授权和撤销

- 确认界面可以提供“记住我的选择，以后不再询问”。
- 长期授权显示主体、能力、范围、开始时间和撤销入口。
- 用户可随时撤销授权。
- 撤销后相关调用立即停止，不等待下一次登录。
- 授权、拒绝和撤销均需要访问记录。

当前创建、实际更新、软删除和单次消费都会生成 `permission_changed` 事件，并与规则变更同数据库事务提交。删除使用 `deleted` 终态保留可追溯记录；默认列表排除该状态，明确按状态筛选时仍可查看。

设备专用授权入口只接受主体、能力和权限等级，把设备能力映射为 `read` 或 `control` 后创建同用户范围的 `resource_type=device` Permission。授权写入同时产生 `permission_changed` 与最小 `device_changed`；它不连接设备、不发现权限，也不代表手机或家电系统权限已经授予。更新、撤销和消费仍以通用 Permission 生命周期为准。

## 当前安全检查流程

```text
请求 → Permission 精确检查 → 风险等级判断 → 确认要求 → 返回 allow / confirm / deny
```

- Security 只能在 Permission 结果上继续收紧，`deny` 和 `forbidden_ask` 不能通过确认变为允许。
- `ask_every_time` 必须产生本次确认；`always_allow` 遇到高风险仍须确认。
- 风险等级为 `low`、`medium`、`high`、`critical`。低风险不要求确认，中风险使用用户自定义确认，高风险和极高风险每次确认。
- 用户自定义确认在正式服务端偏好存储完成前一律安全默认要求确认；请求不能自行关闭确认，它也不能降低高风险最低要求。
- 安全结果中的 `preflightPassed` 表示预检通过，`executionAllowed` 固定为 `false`，`executionStatus` 固定为 `not_executed`；本阶段没有执行器。
- Security 对 `allow_once` 先做非消费预览，只有整条安全链满足时才原子消费，避免确认前丢失单次许可。
- 设备操作准备统一使用 `operationType=device_control`，当前安全策略保守地评为 `critical` 并要求每次确认；即使最终安全检查通过，设备执行状态仍固定为 `not_executed`。

## 操作确认

不可逆或高风险操作即使已有权限，也应说明本次具体内容和后果。这属于操作确认，不是重复申请权限。

需要单独确认的规划类别包括：

- 摄像头和门锁
- 付款和资金能力
- 身份证等身份信息
- 健康数据
- 亲密设备
- 删除数据、账号或主体

当前 Confirmation 基础使用 `not_required`、`every_time`、`user_defined` 三种要求。需要持久化的确认绑定用户、主体、操作类型、资源类型、资源 ID、动作、风险等级、Permission 快照和安全策略指纹；状态为 `pending`、`approved`、`rejected`、`consumed`、`expired`。确认自请求起五分钟内有效，批准结果只能被完全匹配的请求使用一次，不能跨用户、主体、资源、动作、敏感分类、策略或权限版本复用。确认完成不代表真实操作已经执行。

## 敏感信息边界

当前 SensitiveData 模块只包含五类分类元数据：`api_key`、`identity_information`、`payment_information`、`private_record`、`ai_private_domain`。所有分类都声明 `contentAccepted=false`，分类查询接口没有正文写入入口，也不建立敏感正文表。Security 请求拒绝额外字段并要求平台不透明资源 ID；凭据形态拦截只是启发式防线，不是完整 DLP，真实资源接入必须由可信服务端资源注册表提供引用。

- API Key、密码、验证码、付款密码和完整证件号码不进入模型上下文。
- 事件和日志只保存必要的脱敏摘要。
- 穿戴、体重、生理期、亲密、财务和 AI 私域数据按敏感数据处理。
- 中转站和第三方服务必须说明数据去向。
- 用户只能在明确授权范围内连接外部能力。

## AI 安全边界

- AI 输出可能出错。
- 医疗、法律、付款、门锁、摄像头和设备控制等重要事项不能只依赖 AI。
- AI 的建议、权限申请和实际执行是三个不同阶段。
- 平台最低安全规则不能被主体设定、长期要求或用户角色描述绕过。
- 第一版不允许 AI 无限制自动执行。

## 数据权利

用户对与自己有关的数据拥有规划中的查看、纠正、撤销、导出、删除和停用权。隐藏版本、AI 私域和审计记录仍需遵守保留与删除政策，不能形成永久不可见数据。

## 上线前验收方向

- 每项真实能力均能识别权限档位和范围。
- 会话授权能在会话结束后失效。
- 长期授权可查询和撤销。
- 高风险操作不会因已有权限而跳过具体确认。
- 上线前必须验证密钥和敏感原文不会进入模型、事件、日志或 GitHub；当前阶段已覆盖明确秘密字段和常见凭据形态，尚未实现生产级 DLP。
- 跨用户和跨主体权限绕过测试全部通过。

当前阶段已验证基础规则、设备元数据授权、安全预检、短时操作确认、审计和隔离，但真实账号授权、操作系统/厂商授权、真实资源执行、会话失效、可配置确认期限、正式用户偏好、权限申请流程和生产审计保留策略尚未达到上线标准。

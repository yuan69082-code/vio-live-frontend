# 08｜权限、安全与隐私治理

## 当前权限五档

| `permission_level` | Checker 结果 | 含义 |
| --- | --- | --- |
| `always_allow` | `allow` | 在完全匹配的主体、资源实例和操作范围内允许 |
| `ask_every_time` | `ask` | 每次执行前要求明确确认 |
| `allow_once` | 首次为 `allow`，随后为 `deny` | 独立 Checker 首次判断后消费；Security 预检在确认满足前不消费 |
| `denied` | `deny` | 不允许执行，但 `canAsk=true` |
| `forbidden_ask` | `deny` | 不允许执行且 `canAsk=false` |

Permission 本身仍没有“会话级”档位；`allow_once` 是一次性基础权限。Security Policy 的 `session_allow` 已提供独立的开发期短时安全授权：必须使用显式 `securitySessionId`，在具体确认被消费后才建立，绑定完整作用域和策略版本并在 30 分钟后失效。该 ID 不是登录会话或身份凭证，正式认证会话结束联动仍待后续实现。

## 权限粒度

权限不能只做一个总开关，应按以下维度分别表达：

- 用户与智能体主体
- Tool、设备或外部服务
- 数据类型
- 具体动作
- 允许范围
- 有效时间
- 是否可以主动申请

### 当前基础实现

- 每条规则必须绑定用户、主体、资源类型、资源 ID 和具体操作，不支持通配、继承或主体无关规则。
- 资源类型为 `memory`、`tool`、`mcp`、`skill`、`device`、`api`、`private_domain`、`life_data`。
- 基础操作为 `read`、`write`、`execute`、`control`、`connect`、`export`、`delete`、`manage`。
- 状态为 `active`、`inactive`、`consumed`、`deleted`；只有 `active` 参与判断。
- 没有完全匹配的活动规则时默认返回 `deny`，不会因已登录、模型选择或其他资源权限自动放行。

## 授权和撤销

- 确认界面可以提供“记住我的选择，以后不再询问”。
- 长期授权显示主体、能力、范围、开始时间和撤销入口。
- 用户可随时撤销授权。
- 撤销后相关调用立即停止，不等待下一次登录。
- 授权、拒绝和撤销均需要访问记录。

当前创建生成 `permission_created`，实际更新和单次消费生成 `permission_changed`，软删除生成 `permission_revoked`；事件与规则变更在同一数据库事务提交。删除使用 `deleted` 终态保留可追溯记录；默认列表排除该状态，明确按状态筛选时仍可查看。

设备专用授权入口只接受主体、能力和权限等级，把设备能力映射为 `read` 或 `control` 后创建同用户范围的 `resource_type=device` Permission。授权写入同时产生 `permission_created` 与最小 `device_changed`；它不连接设备、不发现权限，也不代表手机或家电系统权限已经授予。更新、撤销和消费仍以通用 Permission 生命周期为准。

## 当前安全检查流程

```text
请求 → Permission 精确检查 → 平台风险分类 → 用户 Security Policy → Confirmation → 返回 allow / confirm / deny
```

- Security 只能在 Permission 结果上继续收紧，`deny` 和 `forbidden_ask` 不能通过确认变为允许。
- `ask_every_time` 必须产生本次确认；`always_allow` 遇到高风险仍须确认。
- 风险等级为 `low`、`medium`、`high`、`critical`。用户默认安全等级只能抬高平台分类，不能降低。
- Security Policy 按用户、资源类型、动作和有效风险精确匹配，规则为 `always_allow`、`session_allow`、`always_confirm`、`deny`、`deny_without_confirm`。
- 用户偏好支持高风险策略、低/中风险自动确认范围和禁止范围；自动范围不能包含 `high` 或 `critical`，禁止范围优先拒绝。
- `always_allow` 和 `session_allow` 不能跳过高/极高风险逐次确认；Permission 拒绝也不能被策略或 Confirmation 绕过。
- 安全结果中的 `preflightPassed` 表示预检通过，`executionAllowed` 固定为 `false`，`executionStatus` 固定为 `not_executed`；本阶段没有执行器。
- Security 对 `allow_once` 先做非消费预览，只有整条安全链满足时才原子消费，避免确认前丢失单次许可。
- 设备操作准备统一使用 `operationType=device_control`，当前安全策略保守地评为 `critical` 并要求每次确认；即使最终安全检查通过，设备执行状态仍固定为 `not_executed`。
- AI 私域读取、写入、管理和导出准备统一使用 `resourceType=private_domain`、`operationType=privacy_access_request` 和 `ai_private_domain` 敏感分类，风险固定至少为 `high` 并逐次确认。通过后只执行本地数据库操作，不调用模型或外部资源。
- 生活数据使用 `resourceType=life_data`，按主体划分 `finance`、`calendar`、`body`、`local-memory` 四个固定资源 ID；读写使用 `sensitive_data_access + private_record`，风险至少为 `high` 并逐次确认。通过后只执行本地 SQLite 操作，不支付、不同步银行/设备、不调用模型。

## 操作确认

不可逆或高风险操作即使已有权限，也应说明本次具体内容和后果。这属于操作确认，不是重复申请权限。

需要单独确认的规划类别包括：

- 摄像头和门锁
- 付款和资金能力
- 身份证等身份信息
- 健康数据
- 亲密设备
- 删除数据、账号或主体

当前 Confirmation 基础使用 `not_required`、`every_time`、`user_defined` 三种要求。需要持久化的确认绑定用户、主体、操作类型、资源类型、资源 ID、动作、风险等级、Permission 快照、Security Policy ID/版本、开发期安全会话和安全策略指纹，并保存平台生成的确认原因、风险说明及用户的 `approve` / `reject` 选择；状态为 `pending`、`approved`、`rejected`、`consumed`、`expired`。确认自请求起五分钟内有效，批准结果只能被完全匹配的请求使用一次，不能跨用户、主体、资源、动作、敏感分类、策略、偏好、会话或权限版本复用。创建确认同时生成最小 `confirmation_required` Event。确认完成不代表真实操作已经执行。

## 用户安全偏好与策略边界

- 未保存偏好时安全默认是 `defaultSecurityLevel=low`、`highRiskOperationPolicy=always_confirm`、空自动范围和空禁止范围。
- 每个用户可为同一资源类型、动作和风险保存一条活动 Security Policy；删除为可追溯软删除。
- `deny` 表示拒绝当前准备但允许未来申请改变规则，`deny_without_confirm` 表示禁止询问；两者都不会执行资源。
- `session_allow` 只在低/中风险明确确认后建立 30 分钟授权，精确绑定用户、主体、策略版本、安全会话、资源实例、动作和风险。
- 策略和偏好变更、策略拒绝及最终安全结果写入最小 AuditLog；策略更新会使旧 Confirmation 和短时授权失配。

## 敏感信息边界

当前 SensitiveData 模块只包含五类分类元数据：`api_key`、`identity_information`、`payment_information`、`private_record`、`ai_private_domain`。所有分类都声明 `contentAccepted=false`，分类查询接口没有正文写入入口，也不建立敏感正文表。Security 请求拒绝额外字段并要求平台不透明资源 ID；凭据形态拦截只是启发式防线，不是完整 DLP，真实资源接入必须由可信服务端资源注册表提供引用。

AI Private Space 是独立业务数据表，不属于 SensitiveData 分类目录本身。私域 API 拒绝凭据和身份秘密字段；Event、AuditLog 和 Export Manifest 不复制正文。当前开发 SQLite 没有生产加密，因此该实现只适用于受控开发环境。

生活数据同样存放于独立业务表而不是 SensitiveData 分类目录本身。财务、月历、身体和本地记忆 Event 不复制敏感原文；当前开发 SQLite 也不具备生产级静态加密，不能作为公开部署的敏感数据方案。

- API Key、密码、验证码、付款密码和完整证件号码不进入模型上下文。
- 事件和日志只保存必要的脱敏摘要。
- 穿戴、体重、生理期、亲密、财务和 AI 私域数据按敏感数据处理。
- 中转站和第三方服务必须说明数据去向。
- 用户只能在明确授权范围内连接外部能力。

## AI 安全边界

- AI 输出可能出错。
- 医疗、法律、付款、门锁、摄像头和设备控制等重要事项不能只依赖 AI。
- AI 的建议、权限申请和实际执行是三个不同阶段。
- 平台最低安全规则不能被主体设定、长期要求或用户角色描述绕过。
- 第一版不允许 AI 无限制自动执行。

## 数据权利

用户对与自己有关的数据拥有规划中的查看、纠正、撤销、导出、删除和停用权。隐藏版本、AI 私域和审计记录仍需遵守保留与删除政策，不能形成永久不可见数据。

## 上线前验收方向

- 每项真实能力均能识别权限档位和范围。
- 会话授权能在会话结束后失效。
- 长期授权可查询和撤销。
- 高风险操作不会因已有权限而跳过具体确认。
- 上线前必须验证密钥和敏感原文不会进入模型、事件、日志或 GitHub；当前阶段已覆盖明确秘密字段和常见凭据形态，尚未实现生产级 DLP。
- 跨用户和跨主体权限绕过测试全部通过。

当前阶段已验证基础规则、用户安全偏好、精确策略、短时会话授权、Permission 生命周期事件、设备元数据授权、安全预检、操作确认、审计和隔离，但真实账号授权、认证会话联动、操作系统/厂商授权、真实资源执行、可配置确认/会话期限、权限申请流程和生产审计保留策略尚未达到上线标准。

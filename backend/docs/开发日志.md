## 2026-08-02｜Vio V1 RFC 8785 提交前定点修复

### 原因与处理

- 提交前验收发现现有 RFC 8785 证据主要集中于正式 conformance vector，对数字、Unicode、属性排序、嵌套结构、UTF-8 和非法输入的独立覆盖不足。
- 新增 9 项独立测试，固定断言 RFC 8785 Section 3.2.2/3.2.3 综合标准向量、Appendix B 代表性数字序列化、UTF-16 code unit 属性排序、Unicode 原序列、UTF-8 字节与 SHA-256，并拒绝非有限数字、孤立代理项和非 JSON JavaScript 值。
- 只读调用本地 Engine `c732f35` 的 `canonicalize_json` 对额外语料进行跨语言比较；canonical JSON、UTF-8 字节和 SHA-256 全部一致。该对照只存在于测试，不构成运行时依赖或连接。
- 新测试暴露字符串末尾孤立高代理项未被拒绝的问题；仅补充 `first-round-hashing.js` 的末尾边界判断，未引入新依赖，也未改变 Schema、哈希向量或机器契约。

### 发现的现状与冲突

- Vio 已有消息、版本、摘要来源、Event、私域安全投影、Permission/Security 和 Token 基础；但没有引擎客户端、助手—引擎主体绑定、请求/投递/回执账本、幂等落库或状态对账。
- Vio 现有 `state_update` API 允许开发调用方推进当前状态指针，缺少 engine revision/update ID/schema/hash；它与“引擎唯一权威”冲突，后续必须收口，历史数据不能自动回灌引擎。
- Vio 现有 Context Service 是只读平台事实投影，不应继续被描述为最终认知 Context。
- continuity-engine 已有 Event → StateMutation → Evolution、revision、重复 Event 防护及 Wake → Perception → Thinking → Action/Learning 链；但只有本地调试/进程内接口，没有面向 Vio 的生产传输、鉴权、租户隔离、平台事实包或外部 Observation 契约。
- continuity-engine 当前使用本地 JSON repository、没有数据库迁移目录；本地 frontend/HTTP 聊天链和 Thinking provider seam 是调试边界，不能让 Vio 前端直连，也不能在真实模型阶段绕过 Vio 的安全模型通道。
- Vio `assistantId` 当前在私域模块映射 Subject ID，而引擎只有自身 `subjectId`；两者尚无正式绑定规则。

### 作出的架构决定

- continuity-engine 是 SubjectState 唯一权威源；Vio 只保存引擎投影、快照、缓存或审计记录，状态冲突时以引擎为准。
- 当时的 v1 设计把 Vio Event 转换为 `stateMutationAllowed=false` 的 Observation；v1.1 后续取消该声明字段，改为 PlatformObservation 结构中完全不存在并严格拒绝任何状态写字段。是否形成内部 Event、StateMutation 和新 revision 始终由引擎决定。
- Vio 只生成经复合归属、Permission、Security Policy 和需要的 Confirmation 筛选的平台事实包；最终认知 Context 由引擎唯一组织。
- AI Private Space 默认不进入事实包，只能按本次目的走独立安全链读取最小投影；引擎回写也只能提出由 Vio重新授权的版本化提案。
- 前端只连接 Vio；数据库保持独立；模型/Tool/MCP/设备由引擎提出调用意图，Vio执行 Token、权限、安全、确认和安全通道。
- `requestId`、Observation、回复和 engine revision/update ID 分层去重；引擎不可用时 Vio 可保存消息和待处理事实，但不能自行回复或推进状态。
